# M2b — Review with Human Identity Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** A human reviewer, talking to an agent, approves, rejects or sends back a submitted proposal. Approval applies the OpenMetadata change sets and realizations **with the reviewer's own OM identity** (token exchange or forwarded token, never the bot), so OM records the real approver. Agents are refused, stale drafts can be rebased, and every decision is audited.

**Architecture:** The dev stack's OpenMetadata moves from basic auth to Keycloak SSO. The bot JWT keeps working for agent operations. A new on-behalf-of module (`core/obo.py`) turns the caller's Lakeloom token into an OM token: RFC 8693 exchange at Keycloak, or forwarding, or failing closed. A per-call `OMClient` carries that token. A new `ReviewService` (`core/review.py`) gates decisions in this order:
1. human principal;
2. `lakeloom:review` scope;
3. the model's review groups;
4. the OM permission check made with the reviewer's token.

It then applies part by part, glossary before native. When a later part's change sets went stale only mechanically (the native working revision moved, or the part references entities created by an earlier part of the same proposal), it is rebuilt from its stored typed operations. Realizations are applied by tagging assets. A shared "rebuild part" primitive in `ProposalService` also backs `rebase_proposal` and editing after `request_changes`.

**Tech Stack:** existing stack (FastAPI, MCP SDK, httpx, SQLAlchemy/Alembic, pydantic); Keycloak 26.8 standard token exchange (V2); no new runtime dependencies.

**Spec:** `REQUIREMENTS.md`:
- FR-REV-01/02/03/05, FR-OM-03/04/05;
- NFR-SEC-03/07/08/09/10/11/12, FR-AGT-03/04/05/06/07;
- the M2 acceptance criteria "an agent principal cannot approve; a Keycloak user approves and OM records that user", and the apply half of "`bootstrap_data_product` flow creates a model from the fixture lake".

This is part 2 of 3 of M2 (M2a proposals — done; M2b this plan; M2c Git publishing on apply). Background: ADR 0011 and `docs/backlog/m2a-deferred.md` § "Carried into M2b".

## Decisions taken in this plan (controller; owner may overrule at plan review)

- **Approve and reject need a confirm token** (FR-AGT-03: approve changes the catalog, reject discards the change sets). The first call returns the summary, the diff and a token; the second call executes. `request_changes` touches nothing in OM and needs no token.
- **`request_changes`** sets the status to `changes_requested` and stores the comment. OM change sets stay SUBMITTED (rc1 has no back-to-draft transition). The owner's next `propose_change` or `rebase_proposal` rebuilds the open parts as new Drafts (bot token). `submit_proposal` is then needed again.
- **OM token for humans:**
  - when `LAKELOOM_OIDC_TOKEN_EXCHANGE=true` (the default), Lakeloom does an RFC 8693 exchange at the issuer's token endpoint, as confidential client `LAKELOOM_OIDC_CLIENT_ID` / `_SECRET`, asking for audience `LAKELOOM_OM_AUDIENCE` (default `openmetadata`);
  - when it is `false` and `LAKELOOM_OM_FORWARD_USER_TOKEN=true`, Lakeloom forwards the caller's token;
  - otherwise it fails closed.

  An exchange error **never falls back** to forwarding or to the bot.
- **"Reviewer permission in OM"** (FR-REV-01) means OM's own permission answer for the reviewer on the model's glossary and native ontology. It is read with the reviewer's token, and the OM endpoint and the permission names come from the Task 2 research. OM still enforces its permissions on apply (defence in depth).
- **Auto-rebuild during apply only for mechanical staleness.** Part k (k ≥ 2) is rebuilt under the reviewer's token when its native `baseWorkingRevision` is behind, or when it references draft ids or versions of entities that an earlier part of the same proposal created. It is rebuilt from the same reviewed typed operations, and the old change-set ids are kept as `superseded`. An operation's own `base_version`, which an agent passed for an existing entity, is never refreshed during apply. A stale one is a `conflict` that leads to `apply_failed`, then `rebase_proposal`, then re-review.
- **Per-model access** (NFR-SEC-07): the `models:` YAML entries gain `access: {propose_groups, review_groups}` (lists of IdP groups). An empty list means no restriction. The CLI operator is exempt, as for ownership in M2a.
- **Deferred, with ADR 0012 entries:**
  - auto-approve policies (FR-REV-04, SHOULD);
  - `min_approvals` (Q6: single reviewer);
  - CLI review (`lakeloom review` would need a human OIDC login flow; the CLI gets `pending` and `rebase` only);
  - Git commits on apply (M2c).

## Review Focus

1. **The wrong principal approves.** An agent token, a human without `lakeloom:review`, a human outside the model's `review_groups`, or a human OM refuses permission to: each gets `forbidden` with a reason naming which check failed. Nothing is written to OM, and the attempt is audited `forbidden`. → Task 5 tests.
2. **Apply fails partway.** OM fails on part 2 of 3, either rejecting it or by going down. The proposal becomes `apply_failed`, recording each part's OM state. Retrying approve skips APPLIED parts and continues; nothing is applied twice. → Task 5 tests.
3. **A stale base at apply.** Another proposal changed the same term after this one was built. The result is `conflict` naming the entity, with hint `rebase_proposal`. Rebase moves it to `draft` and a new submit and review are required. Mechanical staleness between parts of one proposal is rebuilt and never surfaces. → Tasks 4 and 5 tests.
4. **The OM token cannot be obtained.** Cases: the IdP is down, the exchange is refused (400/401/403), exchange is unconfigured, or the token is already expired. Each one fails closed:
   - an unconfigured exchange gives `forbidden` with an operator hint;
   - an IdP that cannot be reached gives `upstream_unavailable`;
   - never the bot, and no token in logs or errors.

   → Task 3 tests.
5. **Concurrent or replayed approvals.** Two reviewers confirm at the same moment, or a confirm token is replayed. Exactly one apply runs; the other gets `conflict` because the previewed state changed. → Task 5 tests.

  5. the status allows the decision: `approve`: submitted | apply_failed; `reject`: submitted | changes_requested | apply_failed; `request_changes`: submitted;
  6. `om = await obo.om_for(principal)`;
  7. `om.get_permissions` on the glossary (and the native ontology if paired) must allow the apply operations identified in Task 2, else `forbidden` "OpenMetadata does not grant <user> review permission on <model>".

  **approve:**
  - Without a token, it returns a `ConfirmPreview` (summary + diff), whose digest includes the reviewer subject and every change set's OM version and state.
  - With a valid token, under the proposal lock, for each part in order:
    1. skip it when all its sides are APPLIED;
    2. rebuild it (`rebuild_parts(..., om=om, submit=True)`) when it is mechanically stale, using the rule in "Decisions";
    3. apply the glossary side, then the native side, with `om`;
    4. record the OM state after each side.
  - **Realizations** follow every part: `add_asset_tags` / `remove_asset_tags` with `om`, idempotently, recorded in `realizations_applied`.
  - **Success:** status `applied`, a `ReviewRecord` with `applied` ids and `om_user` = `applicationResult.appliedBy`, `ModelService.invalidate(model)`, plus a description re-check per Task 2 research (warning when OM dropped it).
  - **`OMConflict` stale_base:** status `apply_failed`, `conflict` naming the entities, hint "call rebase_proposal, then submit_proposal for a new review".
  - **Other failures:** `apply_failed` with progress kept; `OMForbidden` → `forbidden`.
  - **Retrying approve** continues from the first unapplied part.

  **reject:** a confirm token, as for approve. It discards every non-applied change set with `om`; status `rejected`; reason stored.

  **request_changes:** status `changes_requested`, comment stored, no OM call (no token needed).

  Every call writes one audit record with the human principal type (the service audits only when called with an `audit` repo, like M2a).
